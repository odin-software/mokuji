## Task B2: Páginas 5xx para `http.Error(..., "internal error", ...)`

**Files:**
- `internal/server/errors.go`
- Varios handlers que llaman `http.Error` con `internal error`

- [ ] **Step 1: Auditar usos de `http.Error` con strings genéricos**

```bash

```

Tomá nota de los handlers que sirven 5xx con texto plano. Estos rompen la experiencia: el user ve "internal error" en monospace de browser sin chrome.

- [ ] **Step 2: Crear o usar helper en `errors.go` que sirva 500.html**

Verificar si `internal/server/errors.go` ya expone un helper como `s.errs.InternalServerError(w, r, errID)`. Si existe, los handlers deberían usarlo. Si no, agregarlo:

```go
// InternalServerError responde con 500 estilado vía 500.html en vez de
// texto plano. Usar desde handlers cuando un error opaco (DB caída,
// SMTP timeout, etc.) impide servir la respuesta normal.
func (r *Renderer) InternalServerError(w http.ResponseWriter, req *http.Request) {
    w.WriteHeader(http.StatusInternalServerError)
    if err := r.tmpl.ExecuteTemplate(w, "500", errorData{
        RequestID: middleware.RequestIDFromContext(req.Context()),
    }); err != nil {
        // fallback a texto plano si el template falla
        http.Error(w, "internal error", http.StatusInternalServerError)
    }
}
```

- [ ] **Step 3: Reemplazar `http.Error(w, "internal error", 500)` en handlers principales**

Foco en handlers user-facing: `home`, `library`, `releases`, `profile`, `auth`. Los `admin` handlers pueden quedar como texto plano (uso interno).

Patrón típico:

```go
// antes:
if err != nil {
    h.logger.Error("...", "err", err)
    http.Error(w, "internal error", http.StatusInternalServerError)
    return
}
// después:
if err != nil {
    h.logger.Error("...", "err", err)
    h.errs.InternalServerError(w, r)
    return
}
```

Esto requiere que cada handler tenga acceso a `errs` (el renderer). Si el `*Handler` struct no lo tiene, agregarlo a `Config`/`New` y wirearlo desde `main.go`.

Para minimizar el alcance, dejarlo a discreción: si requiere wiring extenso (>5 handlers tocados), reportarlo como DONE_WITH_CONCERNS y solo hacer el helper + 2-3 handlers de muestra. La cobertura completa puede esperar a v0.8.1.

1. **Phase ordering rationale**: A (empty states) → B (microcopy) → C (performance) → D (emails) → E (favicons) → F (dark). Independientes — el orden no genera dependencias. Si una fase queda incompleta (ej. F1 sin gaps detectados), podés taggear igual.

3. **Si los emails causan regresión en el digest worker tests**: el cambio es contenido a templates. Revertir solo `web/emails/digest.html` y mantener el resto. Worker stays stable.

4. **Lighthouse target**: el spec dice Lighthouse ≥ 90 performance. Si el preload no alcanza, considerar agregar self-hosting de fonts en v0.8.1 (process: descargar woff2 de Google, `web/static/fonts/`, ajustar el CSS para usar `@font-face` local). Esto es un task aparte, ~150 LOC.
