# mokuji v1.0 — design

**Fecha**: 2026-05-24
**Autor**: Kendry + Claude (brainstorm)
**Branch**: `version-0-6` (continuará abierta hasta tag v1.0.0)
**Versión base en producción**: v0.5.0

## Objetivo

v1.0 = mokuji "lista para promoción pública". El umbral que justifica
publicarla en Hacker News, comunidades de manga y redes sociales, y que
soporta la mirada de un dev curioso que llega a forkear o self-hostear.

### Criterio de éxito (cuatro tests verificables)

1. **First impression externa**: alguien que llega de fuera entiende qué
   hace mokuji **antes** de signup — landing pública con value prop clara
   + link previews (OG cards) que se ven bien en Slack/Telegram/Twitter.
2. **First-use guiado**: después del signup, el usuario pasa por un
   onboarding de 3 pasos (qué es mokuji + qué monitoreamos + digest
   prefs) y no cae en estados vacíos rough.
3. **Dev curioso convencido en 60s**: README en raíz comunica value prop,
   sources, stack, y deja claro cómo self-hostear o contribuir.
4. **Desktop usable**: a 1440px+, la app no se ve como "mobile estirada".
   Layout con sidebar lateral usa el real estate.

## Estructura del ship

Escalera de minors con tags de verificación, ejecución continua (no hay
gap temporal forzado entre minors — el escalonado es para tener boundaries
claros de commit/release, no para diferir trabajo). Cada minor cierra
un eje verificable; no se mezclan ejes entre minors.

| Versión | Eje | Verificable en |
|---------|-----|----------------|
| v0.6 | Landing | mokuji.org sirve la landing + library order corregido |
| v0.7 | Cara externa completa | Onboarding + auth redesign + splash + OG + desktop sidebar + daily digest backend |
| v0.8 | Pulido | Empty states + microcopy + performance + emails redesign + favicons + dark parity |
| v1.0 | Docs + tag + promo | README rico + self-hosting.md + CONTRIBUTING.md + tag v1.0.0 |

## Insumos externos

Toda la dirección visual y de copy viene del handoff de Claude Design
(`mokuji-ex.zip`, extraído en `/tmp/mokuji-handoff/handoff_extras/`).
El handoff contiene 19 archivos JSX (React in-browser con `createElement`,
inline styles, sin dependencias) que son la single source of truth para
layout, copy y tokens visuales. La identidad ya está parcialmente aplicada
en producción desde v0.5.0 ("01 × 02-type": vermillón + cream + sumi-black,
Albert Sans + Noto Serif JP + IBM Plex Mono).

Mapping handoff → minor:

- **v0.6**: `dx-marketing.jsx`, `dx-marketing-more.jsx`
- **v0.7**: `dx-onboarding-errors.jsx`, `dx-onboarding-more.jsx`,
  `dx-desktop.jsx`, `dx-marketing-more.jsx` (OG cards adicionales)
- **v0.8**: `dx-onboarding-more.jsx` (empty/error states), `dx-emails.jsx`,
  `dx-marketing-more.jsx` (favicons), `dx-dark.jsx`
- **v1.0**: no requiere handoff visual; screenshots para README salen
  de la app real ya implementada

### Caveats del handoff (documentados por Claude Design)

- **Auth con magic link en el design** → traducir copy a OTP de 6 dígitos
  en dos pasos (`auth/start` → `auth/verify`).
- **"Importar .csv / pegar link"** mencionado en `dxo2-empty-lib` →
  eliminar de la copy, no lo soportamos.
- **Lista de fuentes en "conectar fuente"** menciona comick/rss → ajustar
  a "MangaDex + Asura" (lo que realmente integramos).
- **Handle público durante onboarding** → derivarlo del email al crear el
  user (slug autogenerado), no preguntar en wizard; el user puede
  cambiarlo en `/settings` después.

## Diseño por minor

### v0.6 — landing

**Scope**

- Library ordering: **CERRADO** (commit `3b55589`).
- Landing pública en `/` (cuando user no está autenticado).

**Cambios técnicos**

- `internal/home/`: hoy redirige `/` a `/auth` cuando no hay sesión.
  Cambiar a render de landing template; `/auth` queda accesible
  directo y desde el CTA "empezar" de la landing.
- Template nuevo `internal/home/templates/landing.html` con bloques
  hero + features + footer, portado de `dx-marketing.jsx` (mobile)
  y `dx-marketing-more.jsx` (desktop). CSS plano, custom properties
  ya definidas, breakpoint desktop en 1024px.
- OG meta tags básicos en `layout.html` (default card). Las variantes
  se completan en v0.7.

**Verificación**

- Navegar a `/` deslogueado muestra landing, no redirect.
- Lighthouse mobile + desktop ≥ 90 en performance.
- Link preview de mokuji.org en Slack/Telegram muestra OG card default
  (variantes específicas por ruta llegan en v0.7).

### v0.7 — cara externa completa

**Scope**

1. **Onboarding wizard** de 3 pasos, post-OTP, primer login:
   - Step 1: "qué es mokuji" — explicación del producto (cover art
     animado o estático del handoff).
   - Step 2: "qué monitoreamos" — informativo (MangaDex + Asura,
     automático, sin user-config). Reinterpretación del step de
     `dx-onboarding-more.jsx` "conectar fuente".
   - Step 3: "digest prefs" — radio + opt-in: default `weekly`
     (domingos), opción `daily` opt-in explícito, opción `off`.
     Texto enfatiza no-predatory ("nunca te llenamos la inbox").
   - `users.onboarded_at` (timestamp nullable) gates el wizard.
     `NULL` → mostrar; `NOT NULL` → skip directo a `/library`.

2. **Auth redesign** (`auth/start` + `auth/verify`):
   - Layouts portados del handoff con copy traducido a OTP.
   - `auth/start`: input email + "te enviamos un código".
   - `auth/verify`: input 6 dígitos + "código enviado a X" + reenviar.

3. **Splash screen** (PWA load):
   - Layout estático con wordmark + kanji 目次. Implementación: usar
     campos `splash_screens` (iOS) y background_color + theme_color
     (Android/desktop) del `manifest.json` para que el OS muestre el
     splash al lanzar la PWA instalada. No requiere endpoint server-side.
   - Para usuarios no-PWA (browser normal), el splash NO aplica (cae
     directo a landing o `/library`).

4. **OG meta tags + hasta 6 variantes de cards 1200×630**:
   - Inspeccionar `dx-marketing.jsx` y `dx-marketing-more.jsx` al portar
     para conteo exacto. Variantes conocidas: default, release,
     self-host, minimal, más las 3 del marketing original (posible
     overlap, se confirma al portar).
   - Cada variante mapea a un meta tag `og:image` en la ruta
     correspondiente (default en `/`, self-host en futuro link a
     `/self-host` o en README rendering, etc.).
   - Generar como imágenes estáticas exportadas desde el handoff a
     `internal/home/static/og/`, servidas vía `http.FileServer`. No
     render dinámico server-side (over-engineering para v1.0).

5. **Desktop layout con sidebar** a 1440px:
   - Portado de `dx-desktop.jsx`: home, biblioteca, entry.
   - Breakpoint en 1024px (sidebar aparece). En <1024px se mantiene el
     layout mobile actual (max-width 42rem centrado).
   - Sidebar es nav lateral (library / releases / settings / logout)
     + footer con versión.

6. **Daily digest backend** (feature nuevo, no sólo UI):
   - Migration: `ALTER TABLE users ADD COLUMN digest_frequency TEXT NOT NULL DEFAULT 'weekly'`
     (valores `weekly` | `daily` | `off`).
   - Worker `internal/releases/digest`: agregar tick diario (9-22 UTC
     ventana por día, similar al actual del domingo). Para users con
     `digest_frequency='daily'`, dispatch diario; para `'weekly'`,
     dispatch sólo domingo (comportamiento actual); para `'off'`,
     nunca. Tabla `digest_runs` ya soporta múltiples corridas por día.
   - Settings: nuevo control en `/settings` (radio o select)
     que también edita `digest_frequency`. Tres opciones, weekly por
     default.
   - Onboarding step 3 escribe `digest_frequency` y `onboarded_at`
     en el mismo POST.

**Cambios técnicos resumidos**

```
internal/auth/templates/        → start.html, verify.html redesigned
internal/onboarding/            → handler nuevo + 3 templates
internal/home/templates/        → splash.html, landing.html (de v0.6)
                                  con OG variants en layout.html
internal/profile/handler.go     → settings añade digest_frequency
internal/releases/digest/worker.go → tick daily + dispatch por freq
migrations/                     → 00XX_users_digest_frequency.up.sql
internal/home/static/og/        → 6 PNGs de OG cards
```

**Verificación**

- User nuevo: signup → OTP → onboarding 3 pasos → `/library`.
  `onboarded_at` se llena en step 3.
- Users existentes a la hora de la migration: la misma migration hace
  `UPDATE users SET onboarded_at = created_at WHERE onboarded_at IS NULL`
  para que no vean el wizard. Esto es obligatorio, no opcional —
  forzar onboarding a usuarios ya activos es predatory.
- Daily digest: crear test user, setear `digest_frequency='daily'`,
  forzar trigger admin, verificar envío.
- Desktop 1440px: sidebar visible, contenido no estirado.
- Auth: copy en español dice "código", no "magic link".

### v0.8 — pulido

**Scope**

1. **Empty states completos** (de `dx-onboarding-more.jsx`):
   - `/library` vacía: hero con CTA "agregar tu primer manga".
   - `/library` search sin resultados: "no encontramos X" + sugerencia.
   - `/releases` vacía: ilustración + "todavía no hay caps nuevos".
   - `/u/{slug}` vacía (perfil sin entradas públicas): mensaje breve.
   - Offline (PWA service worker fallback): hero con kanji + "sin
     conexión, reintentá cuando vuelvas".
   - Fuente desconectada (manga sin matches activos en source): badge
     visible en `/library/entry/{id}` + CTA reintentar.

2. **Microcopy / errores**:
   - Pasada de revisión de todos los flash messages, errores de
     validación, labels de form, copy de 404/500.
   - Voz consistente con landing y onboarding (referencia: la voz
     del handoff). Español rioplatense/neutro, tuteo donde aplique.
   - Salir con una guía de voz mínima documentada en `CONTRIBUTING.md`
     (sub-sección).

3. **Performance**:
   - Auditar CSS inline en `layout.html` (hoy es grande por todos los
     tokens y componentes en `:root`). Decidir: mantener inline (cero
     RTT) vs externalizar (cacheable). Recomendado: mantener inline,
     pero medir.
   - Auditar fonts: 3 familias de Google Fonts (Albert Sans + Noto
     Serif JP + IBM Plex Mono). Decidir: self-host con subsetting
     (mejor LCP, sin third-party RTT) vs mantener Google (más simple).
     Recomendado: self-host con subsetting latin + japonés básico.
   - Métrica objetivo: Lighthouse mobile ≥ 90 performance en `/`,
     `/library`, `/releases`.

4. **Email templates redesign** (`dx-emails.jsx`):
   - Comparar templates actuales (digest, OTP, account-deletion)
     contra handoff. Cerrar gaps de layout/copy.
   - Mantener multipart text+HTML, `List-Unsubscribe` headers, etc.
     (no tocar comportamiento, sólo presentación).

5. **App icons + favicons sheet** (de `dx-marketing-more.jsx`):
   - Set completo: favicon.ico, apple-touch-icon, 192/512 PWA,
     maskable icon. Sustituir los actuales por los del handoff.

6. **Dark mode parity** (`dx-dark.jsx`):
   - Validar que cada vista coincide con la variante dark del handoff.
   - Hoy usamos `@media (prefers-color-scheme: dark)` con tokens
     override en `:root`. Posibles gaps: imágenes/ilustraciones que
     necesitan variante dark, hairlines que se pierden, etc.
   - Aceptar diff y publicar.

**Verificación**

- Cada empty state se puede provocar manualmente en local y mostrar
  copy + CTA correcto.
- Lighthouse ≥ 90 mobile en las 3 rutas core.
- Network tab muestra cero requests a fonts.googleapis.com.
- Toggle de OS a dark mode no rompe ninguna vista (smoke test visual).

### v1.0 — docs + tag + promoción

**Scope**

1. **README.md rico** (raíz del repo):
   - Hero: wordmark + 1-line value prop + link a mokuji.org.
   - Screenshot (de la app real, post-v0.8).
   - "Qué hace": 3 bullets — biblioteca privada, releases multi-source,
     digest opt-in.
   - "Stack en una línea": Go + SQLite + stdlib net/http + server-rendered.
   - Sources soportadas (MangaDex + Asura, con disclaimer "Asura opt-in
     env var").
   - Quickstart self-host: link a `docs/self-hosting.md`.
   - Status badges: CI, versión, licencia.
   - Licencia: AGPL-3.0 con explicación de qué implica para forks.

2. **docs/self-hosting.md**:
   - Prerequisitos (Linux + systemd + nginx, recomendación, no único path).
   - Bajar binario (link a releases de Forgejo).
   - Env vars mínimas explicadas (DB_PATH, BASE_URL, SMTP_*).
   - Unit systemd de ejemplo (Type=simple por ahora; nota sobre futuro
     Type=notify).
   - nginx reverse proxy de ejemplo.
   - Resend gotcha (puerto 2587, no 587, en Droplets DO).
   - Migración corre al startup automáticamente.
   - Update path: bajar binario nuevo, systemctl restart.
   - Troubleshooting: dónde miran logs (`journalctl -u mokuji`),
     dónde está la DB, cómo hacer backup.

3. **CONTRIBUTING.md**:
   - Cómo correr local (`make run`, `air`).
   - Cómo correr tests (`make test`).
   - Convención de commits (subject corto, español, lowercase).
   - Cuándo ADR (decisiones arquitectónicas con tradeoff real).
   - Flow de PRs: issue/discusión previa para cambios grandes,
     PR para fixes/polish.
   - Sub-sección "voz" con la guía de microcopy de v0.8.
   - Code of conduct breve.

4. **Tag y release**:
   - Bump `VERSION` a `v1.0.0`.
   - Commit + tag anotado.
   - CD deploya automático a mokuji.org.
   - Release notes en Forgejo (puede ser literal el changelog desde
     v0.5.0 agregado).

5. **Promoción** (fuera de scope técnico del spec, mencionado para
   completitud):
   - Tuit / post HN / posts en comunidades manga. Decidido por el
     user al cerrar v1.0.

**Verificación**

- README en `https://git.odin.do/odin/mokuji` lookea profesional.
- Clonar repo + leer self-hosting.md + bajar binario debería
  llevar a una instancia corriendo en menos de 15 min (test con
  un VPS limpio si tenemos).
- `curl https://mokuji.org/version` devuelve `v1.0.0`.

## Fuera de scope (explícito para v1.1+)

Estos ítems estuvieron en el backlog pero se descartan deliberadamente
de v1.0:

### Diferidos a v1.1+ (probable next milestone)

- **Activity feed / capa social** sobre `/u/{slug}`. Diferido porque
  no es bloqueante para promocionar y agrega riesgo de complejidad
  sin validación previa.
- **Bato.to como 4ta source**. Más cobertura pero requiere scraping HTML
  (overlap con MD). Reabrir cuando v1.0 esté validado.
- **Vincular source manualmente user-facing**. Mini-form con
  search por source + selección de candidato. ~150 LOC + tests.
  El matching automático contra alt_titles cubre 90% real.
- **Email templates avanzados**: cualquier polish post-handoff que no
  esté en `dx-emails.jsx` (ej. milestone emails, weekly recap distinto
  al digest, etc.).
- **OG cards dinámicos por release o por perfil** (server-side render
  con PNG generado al vuelo). En v1.0 son estáticas.

### Diferidos por requerir más research

- **Passkeys / WebAuthn**. Research, no implementación. Cubre flujo
  de registration/authentication ceremony, origin-binding, storage,
  recovery, fallback. Pendiente como ADR o doc de exploración.
- **Comick.app como source**. Bloqueado por Cloudflare managed
  challenge — requiere sidecar tipo FlareSolverr y rompe el shape
  de single-binary. Reabrir si comick relaja bot detection.

### Diferidos a backlog operacional

- **Admin tool `POST /admin/link-source`** (vincular sources manualmente
  no-user-facing).
- **`GET /admin/digest-status`** para observabilidad sin SSH (~30 LOC).
- **`Type=notify` con `sd_notify`** para readiness real en systemd.
  Bajo hasta zero-downtime restart o dependencias.
- **Soporte SMTP `:465`** (TLS implícito) para self-hosters. Hoy
  STARTTLS cubre 99% casos vía 587/2587/2525.
- **CI: tests en workflow antes de deployar**. Intentado y rollback;
  necesita cache de módulos + timeout explícito o workflow separado.

### Descartados (no entran ni en v1.1)

- **Rating** (puntuación de manga). Explícitamente fuera de MVP por
  decisión de producto desde v0.x.
- **Import .csv / "pegar link" para agregar manga**. Mencionado en
  handoff `dxo2-empty-lib`, descartado por scope.
- **"Conectar fuente" como selector real**. El step del wizard es
  informativo, no configurable. Sources siguen siendo backend
  (MangaDex siempre on, Asura opt-in vía env var ya existente).

## Riesgos y mitigaciones

| Riesgo | Probabilidad | Impacto | Mitigación |
|--------|--------------|---------|------------|
| Daily digest backend = scope creep oculto | media | medio | Salida de emergencia: shipping con `weekly` y `off` solamente, `daily` queda a v1.1. La columna ya soporta el valor `daily`, sólo se desactiva el step del wizard y el tick del worker. |
| Volumen del handoff (19 archivos JSX → `html/template`) | alta | medio | Portar de a uno por vista. No tratar el handoff como blocking: si algún detalle no cierra, lookear el JSX como referencia visual y resolver inline. |
| Auth OTP vs design magic-link | baja | bajo | El layout del verify-step acomoda input de 6 dígitos sin cambio estructural. Solo el copy cambia. |
| Performance: fonts pesan demasiado | media | medio | Si self-host con subsetting no rinde ≥90 mobile, evaluar reducir a 2 familias (Albert Sans + IBM Plex Mono, Noto Serif JP solo donde sea decorativo) o usar `font-display: swap` agresivo. |
| Migration de `users.onboarded_at` molesta usuarios existentes | media | bajo | Backfill en la misma migration: `UPDATE users SET onboarded_at = created_at WHERE onboarded_at IS NULL` para que usuarios existentes no vean el wizard. |
| Schedule slip ("se hara todo hoy con suerte") | alta | bajo | Los tags v0.6, v0.7, v0.8, v1.0 son hitos verificables independientes. Si no se termina en una sesión, cada minor tagueado sirve como checkpoint deployable. |

## Decisiones cerradas en este brainstorm

- v1.0 = "shareable / lista para promoción pública", criterio en 4 tests.
- Escalonado en 4 minors (v0.6 → v0.7 → v0.8 → v1.0), no big-bang.
- Eje social (activity feed) **fuera** de v1.0; diferido a v1.1+.
- Daily digest opt-in **dentro**, default weekly, NUNCA predatory.
- "Conectar fuente" reinterpretado como informativo.
- Auth screens redesign **dentro** de v0.7 con copy traducido OTP.
- Emails redesign **dentro** de v0.8.
- Order de ejes: cara externa → pulido → docs. Orden secundario al hecho
  de que probablemente se ejecute todo seguido.
